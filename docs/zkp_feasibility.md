# ZKP 可行性备忘录：API 调用记录完整性证明

> 产品：ai-attestation  
> 性质：**前瞻性研究**，无代码实现  
> 日期：2026-07-19  
> 结论摘要：短中期优先哈希链 + 外部时间戳/锚定；ZKP 适合「对外披露完整性但不暴露明细」的后续阶段。

## 1. 问题陈述

能否用零知识证明（ZKP）向第三方证明：

> 「某段时间内，某 API Key 下的全部 API 调用记录已完整纳入防篡改哈希链，且未被增删改」

同时**不暴露**具体 endpoint、费用、模型或请求元数据？

## 2. 技术可行性评估

| 维度 | 评估 |
|------|------|
| 理论可行性 | **高**。Merkle/哈希链头 + 承诺方案可证明集合完整性。 |
| 实用可行性（MVP） | **低**。证明生成成本、电路维护、审计方工具链均超出当前产品阶段。 |
| 与现有架构契合度 | **中高**。当前 SHA-256 链已是自然承诺；ZKP 可包在「链头 + 计数」之上。 |

### 2.1 可行构造（概念）

1. **承诺**：对时段 \(T\) 内每条调用计算叶子  
   \(L_i = H(\text{call\_id}\|H(\text{private\_fields})\|H(\text{public\_fields}))\)，建 Merkle 树，根 \(R\)。
2. **公开输出**：\(R\)、调用条数 \(n\)、费用总和区间（可选）、链头哈希、时间戳/链上锚定。
3. **证明**：电路断言  
   - 叶子来自合法格式；  
   - Merkle 路径正确且 \(n\) 匹配；  
   - \(R\) 已绑定到已锚定的链头（或链头等于 \(H(R\|\ldots)\)）。
4. **验证**：验证者只看 \(R,n\) + 证明 + 外部锚定，看不到明细。

可选增强：费用总和用 Pedersen 承诺 + range proof，证明「总费用 ∈ [a,b]」而不泄露精确值。

### 2.2 技术选型参考（不实现）

| 方案 | 优点 | 缺点 |
|------|------|------|
| Circom + snarkjs (Groth16) | 生态成熟、验证快 | trusted setup；电路对变长列表麻烦 |
| Halo2 / Plonkish | 透明 setup、递归友好 | 工程与审计成本更高 |
| STARKs | 无 trusted setup、抗量子叙事 | 证明体积大 |
| 简单 Merkle + 开放审计 | 已近似「可验证完整性」 | **非**零知识，明细需按需披露 |

对「完整性」 alone，**公开 Merkle 根 + 哈希链锚定**往往已够用；ZKP 的增量价值主要在**隐私**。

## 3. 适用场景

**适合**

- 客户向监管/客户展示「日志未删改」，但不能给原始调用清单（含商业敏感 endpoint）。
- 多租户 SaaS：证明计量公平（条数/费用区间）而不交叉泄露租户流量形态。
- 并购/SOC 尽调：提供可验证摘要，细粒度证据仍走 NDA 流程。

**不适合（当前）**

- 替代司法鉴定级时间戳（仍需 RFC3161/OTS/链上锚定）。
- 实时代理热路径（证明生成延迟与 CPU 不适合 &lt;50ms 目标）。
- 替代合规检查模板的法律解释。

## 4. 实现复杂度估算

| 工作包 | 人周（粗估） | 说明 |
|--------|--------------|------|
| 电路：固定上限 N 条叶子的 Merkle 成员 | 3–5 | N=1024/4096 分档 |
| 证明服务（批处理离线生成） | 2–3 | 与代理解耦 |
| 验证 SDK + `/verify` 集成 | 1–2 | 复用现有独立验证页 |
| 安全审计 + trusted setup 仪式（若 Groth16） | 4–8 | 外部审计为主 |
| **合计（可演示原型）** | **~10–18** | 不含硬件加速 |
| **生产级（审计+密钥+运维）** | **~25–40+** | 视合规要求 |

相对地：完善 OpenTimestamps / RFC3161 + 周期链头锚定约为 **1–2 人周**，且已覆盖「存在性 + 未篡改」的大部分对外叙事。

## 5. 建议路线

1. **现在**：哈希链 + 独立时间戳 +（mock/Sepolia）锚定 + 可分享验证包（已实现方向）。  
2. **下一步**：公开 Merkle 摘要导出（仍非 ZK），满足多数 B2B 审计。  
3. **再下一步**：仅当出现明确「要证明完整性又不能给明细」的付费客户时，启动 Circom/Halo2 原型。

## 6. 风险与边界

- ZKP 不创造法律效力；证明的是数学陈述，不是「已合规」。  
- 错误电路 = 虚假安全感；必须外部审计。  
- 叶子若包含可关联伪匿名 ID，仍可能被流量分析去匿名。

## 7. 结论

**可以用 ZKP 证明时段内 API 调用记录完整性而不暴露明细**，技术路径清晰，但 **MVP 不应实现**。当前产品应继续强化可独立验证的哈希链、时间戳与锚定；将 ZKP 保留为候选增强，待隐私披露成为明确付费需求后再立项。
